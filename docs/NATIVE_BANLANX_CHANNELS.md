## Status and transport
Native does not treat demo, cached defaults, a successful power write or entry into a route as actual ON state. Only an explicit Read action dispatches8F through the existing queue. A complete88-byte current-device/characteristic/BLE-session status whose first valid seq1 fragment arrived AFTER that request was actually dispatched establishes Native status. A frame begun before the request, or while its write is still queued, cannot establish Native authority even if its tail arrives later. The legacy frame buffer/cache remains unchanged. Partial/invalid reports, another write, leaving, reconnect and background invalidate it; legacy channel caches are not modified. Read times out after5seconds as a disclosed browser safeguard. Because the protocol has no query nonce, delayed old complete reports within the SAME connection cannot be uniquely correlated; this is latest observed status, not a hardware freshness guarantee.

Power requires an explicit status read, visible current route, actual BLE (not canSend/demo), parked/decorative consent and no competing cart flow. Every82 write uses the existing serialized queue with revocable guards checked before enqueue and after pacing. No optimistic ON changes or automatic refresh commands follow. A write may already be physically in flight when navigation/consent is revoked; no promise to recall it is made.

No83/85/89, group/scene/trigger/timer writes, rename, connection initiation, storage migration or calibration change is implemented. The real control-screen destination preserves the exact source mask but remains unavailable until its verified disk component is integrated. Route cancellation and read provenance are separate requirements for that next stage; do not initialize an authored target from calibrated wire RGB.
